# unk_0200FA24

Screen fade, the HBlank hook it uses and the hardware-window reset.

## Layout recovered

- `_021D0EF4` is one `FadeCtrl` (0x154 bytes). The asm splits the bss into `_021D0EF4`, `_021D0EF8`, `_021D0EFC`, `_021D0F08`, `_021D0F38`, `_021D0F68`, `_021D0F80` and `_021D1034`; they are all fields of this struct:
  - +0x00 fade order, +0x04 / +0x08 main / sub "still running", +0x0C / +0x10 main / sub enabled
  - +0x14 and +0x44 two `FadeWork` records (0x30 bytes each; +0x00 fade type, +0x10 screen, +0x24 colour, +0x28 and +0x2C state words written by the `FadeFunc_*` code)
  - +0x74 the HBlank block (0x18 bytes: two args, two callbacks, two enable flags)
  - +0x8C the hardware-window block (0xC0 bytes, handed to `sub_02013424` and friends)
  - +0x14C fade running (u16), +0x14E / +0x14F main / sub flags (u8), +0x150 last colour (u16)
- `HandleEndFade` tests `[ctrl + 0x3C]` (the main work's state word) for both the main and the sub clean-up, not `[ctrl + 0x6C]`. The C keeps that (`ctrl->main.unk_28` in both places).
- `sFadeFuncPtrs` (rodata in this asm file) is declared extern, not redefined: `CallFadeFunc` indexes it with a value read from memory, and the sandbox compares reads past the table against the ROM.
- `sub_0200FECC` is written unrolled (two calls) instead of as a two-iteration loop. The loop form compiles to a call with `r2` clobbered, and the sandbox compares the leftover argument registers of an indirect call; the original leaves `r2` and `r3` untouched. Behaviour is the same.

## Functions the sandbox cannot confirm on the real file (all 9 show FAIL in the ledger)

Tail calls. The original ends in `ldr r3, =target; bx r3`. The sandbox does not follow a jump out of the function, so the original side never "returns" and the comparison stops with "only one side returned". The C is a plain call of the same function with the same arguments:

- `ResetVisibleHardwareWindows` -> `sub_020131F4(0, screen)`
- `SetMasterBrightnessNeutral` -> `SetMasterBrightness(screen, 0)`
- `sub_0200FBF4` -> `SetMasterBrightness(screen, brightness)`, with brightness 16 when the colour is 0x7FFF (0xFFFF means "use the stored colour") and -16 otherwise

Addresses of functions defined in the same C file. `arm_link.py` sends a call to a function the game has to the game's address, but a function address used as data (stored in memory or passed as an argument) is relinked to the copy placed in the test blob, so the pointer values differ (`0x2380xxx` against `0x0200xxxx`):

- `sub_0200FEB0`, `sub_0200FF5C` (store `sub_02010014` into the HBlank block)
- `sub_0200FEE4` (passes `sub_0200FECC` to `Main_SetHBlankIntrCB`, stores `sub_02010014`)
- `sub_0200FF88` (passes `sub_0200FFD8` to `SysTask_CreateOnVWaitQueue`)
- `sub_0200FFB4` (passes `sub_0200FFF8`)
- `sub_02010064` (passes `sub_02010050`)

All six PASS (500 of 500 trials) on a scratch copy of the file with the callbacks `sub_02010014`, `sub_0200FECC`, `sub_0200FFD8`, `sub_0200FFF8` and `sub_02010050` declared extern instead of defined, so the pointers resolve to the game's addresses. The callbacks themselves PASS in the real file.
