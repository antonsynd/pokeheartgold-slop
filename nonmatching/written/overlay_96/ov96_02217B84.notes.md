Builds 12 sprite entries (index k: row k / 3, column k % 3) and then initialises 4 more (stride 0xa8), as in the asm; every
callee has its full prototype (no .arities.json).

Two things in the asm read its own stack frame, and `img[16]` in the C stands for that frame from sp+0x30 to the entry sp
(the asm's frame is 0x5c bytes, then saved r4-r7 and lr, entry sp = asm sp + 0x70):
1. The first loop reads the 6-word block at sp+0x44 (zeroed, then passed to ReadWholeNarcMemberByIdPair) at
   `sp + 0x3c + 8 * i` and `+ 0x40 + 8 * i`, where i is the return of ov96_021E6138. In the game i is 0..3 (that function
   returns the 0..3 kind of its argument), but the check's stub returns any 32-bit value. The read is reproduced for every
   i: the offsets inside img (the outputs at sp+0x38/0x3c/0x40, the block, the saved registers) read img; any other offset
   reads memory relative to the entry sp (`__builtin_frame_address(0) + 8` under the check's clang -O0 Thumb build). The
   caller's r4/r5/r6 are read with inline asm as the first statements, r7 from the frame record, lr from
   `__builtin_return_address(0)`. The C is exact for in-range i; offsets below sp+0x30 (the asm's other locals, only
   reachable with i between -8 and -1) are not modelled.
2. ov96_021EB0A4 takes the output pointer sp+0x30 / sp+0x38 as a stack argument. The stub only fills register arguments, so
   the slot is read back unwritten, as in the asm (uninitialised stack in both); `img[0]`/`img[2]` are left uninitialised on
   purpose.
