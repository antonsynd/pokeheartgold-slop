# ov96_021FF2A0: PASS

The asm keeps the objects it passes to callees (and reads back after them) in its own frame. With
asm_sp = entry_sp - 0xb8 (push {r4-r7, lr}, then 0xa4 bytes): the position pair at +0x24, the target pair at +0x1c,
sub_02020F4C's output vector at +0x2c, the segment point at +0x78, the offset vector at +0x6c, the VEC_MultAdd
operand at +0x60 and its result at +0x54. The check does not run the callees, so the original reads those output
words as they were (and compares the pointers it passes). The C passes and reads them at the same addresses
(`__builtin_frame_address(0) + 8 - 0xb8 + off`, the entry sp under the check's clang -O0 Thumb build); the first local
`framePadding[0x90]` keeps the C's own locals out of that part of the frame. This is compiler-layout dependent but
deterministic for the check's flags. The two stack copies of the ROM tables ov96_0221C5FC / ov96_0221C60C (indices
0..3 only) are read straight from the ROM tables.

The fifth argument (param_5) lives in the caller's frame at entry_sp, and on the first-phase hit path the asm stores
the advanced pointer back into that slot (visible write), so the C does the same. The original's first
`ldr/str [sp, #0xb8]` pair rewrites the slot with its own value (no effect).

The `cmp r4, #0; bne; cmp r4, #2; bne` block at 0x021FF34C can never take its r4 == 2 arm (r4 == 0 is excluded
first), so the C has only the x/y-range arm. The final block's `ip == 0 && r1 == 0` exit is unreachable.
Loads are kept in the asm's order (param_2/param_4 are re-read after the stores to param_5 in case they alias).
