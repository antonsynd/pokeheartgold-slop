# Decompiling what's left of an hgify-split asm file

hgify (PRs #6 and #10) replaced some asm files with a run of objects in
`main.lsf`: one generated C file per matched function in
`src/hgify/<base>/<base>_NN.c` (first line `// Generated by hgify/integrate.py`;
a few live in `src/field/` or `src/frontier/`), asm slices `asm/<base>_NN.s`
holding the rest, and `asm/<base>_data.s`. Re-integrations renamed the pieces
(`_rNN`, `_sNN`, `_tNN`, ...; `_vNN` for a function kept in asm because it
depends on the game version); read `_NN` below as any of these.
`hgify_marks.py` holds the markers and the piece-name pattern that every script
uses.

Generated C files could also keep a function as inline asm. Since #10 none do,
so every unit today is an asm slice, but the tools still handle this shape:

```c
// FUNCTION ov99_021E5B90: no matching C yet, the original asm
// clang-format off
asm int ov99_021E5B90(int param_1, int param_2) {
    ...
}
// clang-format on
```

The original `asm/<base>.s` stays in the tree but is no longer linked, so it is
not a target itself. `next_target.sh` serves its **units** one at a time and
tags them `[SPLIT unit of asm/<base>.s]`:

| Unit | What it holds | Workflow |
|---|---|---|
| `asm/<base>_NN.s` | a linked asm slice | the usual one, below |
| `src/hgify/<base>/<base>_NN.c` | a generated file with inline asm (none since #10) | rewrite in place, below |

Data-only slices (`asm/<base>_data.s`, and slices without functions) are not
units. The generated C extern-references that data, so moving it to C changes
the whole split file, not one piece of it. Leave them in asm.

`python3 tools/decomp_harness/split_units.py base <path>` tells you whether a
path belongs to a split file (prints `asm/<base>.s`, else exits 1);
`split_units.py units asm/<base>.s` lists the pending units (leaving out those
recorded completed or failed in progress.json) and `split_units.py funcs <unit>`
the functions still in asm in one. The ledger lists each split file as one
matched row plus one pending row marked `split`, which triage ranks after the
untouched files; `next_target.sh` serves that file's next pending unit.

These are the functions hgify's scripts could **not** match, so expect them to
be harder than the queue's untouched files. The draft's behaviour is still right.

## Common to both

- **Claim the original file**, not the unit: `claim.py open asm/<base>.s`. One
  claim covers all its units. Unit commits say `Refs #N`; the commit after which
  `split_units.py units asm/<base>.s` prints nothing says `Closes #N`. Don't
  `claim.py close` after a failed unit: the other units are still yours.
- **Prior knowledge** is keyed by the original file and by function:
  `attempts_log.py query --file asm/<base>.s` (log with that `--file` too), and
  `twins.py func <fn> --show` for each function `split_units.py funcs <unit>`
  prints.
- **progress.json**: record the unit path as `file` (that is what
  `next_target.sh` skips). `matched` only when every function in the unit is C;
  otherwise `failed` with a `reason`.
- **Revert** with `./tools/decomp_harness/revert.sh <unit>`. It restores a
  tracked generated file from HEAD rather than deleting it, and removes the
  unit's build object, so rebuild before saving a new reference.
- After a unit lands, run `triage.py --rebuild` as usual. Skip `twins.py prune`:
  it only knows `src/<name>.c` for `asm/<name>.s`, not split files.

## A slice: `asm/<base>_NN.s`

The normal `/decomp` workflow with `<basename>` = `<base>_NN`: write
`src/<base>_NN.c` (top level of `src/`, not `src/hgify/`: it's hand-written), flip `Object asm/<base>_NN.o` → `Object src/<base>_NN.o`, and
`compile_one.sh src/<base>_NN.c` objdiffs against `build/heartgold.us/asm/<base>_NN.o`
by itself. Differences:

- There is no `asm/include/<base>_NN.inc`; the slice includes the original
  `<base>.inc`. Imports vs exports: a symbol is defined here only if the slice
  has its `thumb_func_start`/`arm_func_start`.
- Write ordinary pret-style C with real headers. The neighbouring generated
  files' Ghidra style (`undefined4`, local prototypes) is not something to copy.
  They declare the slice's functions with their own local prototypes, so you
  don't need a header for them.

## A generated file with inline asm: `src/hgify/<base>/<base>_NN.c`

None exist since #10; this is for when one appears. Below, `src/<base>_NN.c`
stands for the generated file's path.

No `main.lsf` change: the file is already linked as C. Replace each inline-asm
function with C, in place:

1. **Save the reference** from a build of HEAD before editing:
   `cp build/heartgold.us/src/<base>_NN.o /tmp/<base>_NN_ref.o`
2. For each function `split_units.py funcs src/<base>_NN.c` prints, replace the
   `// clang-format off` / `asm ... { }` / `// clang-format on` block with C and
   change its marker to `// FUNCTION <fn>: matching C (manual)`.
   `tools/update_readme_progress.py`, `coverage_ledger.py` and
   `split_units.py funcs` count functions by those markers (`hgify_marks.py`),
   so a converted function with the old marker is still counted as asm.
3. Stay in the file's style (its existing types and local prototypes). The file
   is one TU under `-ipa file`: a new declaration or a changed prototype can move
   the codegen of functions in it that already match.
4. `tools/decomp_harness/compile_one.sh src/<base>_NN.c --ref /tmp/<base>_NN_ref.o`
   must show **every** function in the object matching, not only the one you
   converted. (A missing `--ref` file is an error, not a silent compile-only run.)
5. A function that won't match keeps its asm block. It is already the fallback,
   so no NONMATCHING block is needed, but log the dead ends.
6. Finalize as usual: full `compare` (ROM SHA1).
